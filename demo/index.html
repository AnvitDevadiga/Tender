Independent verification for AI-generated code

Tender verifies AI-generated code before you trust it.

Point Tender at a repository, a pinned commit, a patch from any coding agent, and acceptance criteria written before the patch ran. It applies the patch in fresh, isolated workspaces, runs your target and regression checks, and keeps a hash-sealed record of every command and result.

Open the recorded demo See a failure and its repair Source on GitHub

The hosted demo is read-only. It replays recorded runs and reports; nothing executes on this site. A pass means the configured checks passed in a clean workspace, not that the code is free of defects.

01 · How Tender evaluates code

The patch is untrusted. The judge is not.

Every check runs in a workspace created from Git objects at the exact base commit. Earlier attempts, uncommitted edits, and ignored files cannot leak in, and evaluator-owned files are reset before anything runs.

  1. 01

    Pin

    Resolve the base commit from a sanitized, read-only copy of the repository's Git metadata. Repository hooks and helpers never run on your machine.

  2. 02

    Validate

    Reject malformed patches, path traversal, symlinks, binaries, oversized changes, and edits to evaluator or protected files before any code runs.

  3. 03

    Isolate

    Apply the patch to a fresh workspace for each check. Reset test files and runner configuration to the base commit; add hidden checks only now.

  4. 04

    Verify

    Run a baseline, then target and regression checks, inside a network-disabled Docker container. Each test must be reported as passed by name.

  5. 05

    Record

    Write commands, exit codes, outputs, digests, timings, and what remains unknown into an evidence bundle with a SHA-256 per file.

Runs on your machine

Tender itself: Git plumbing on sanitized metadata copies, patch validation, report writing. Never repository code.

Runs in Docker

Setup, baseline, target, and regression commands. No network, dropped capabilities, read-only root, bounded CPU, memory, and time.

Runs on this website

Nothing. The pages render recorded JSON. Reports and runs carry labels: recorded, derived, unknown, verified.

04 · Reproducibility

Rebuild every number from a fresh clone.

Fixtures are generated with fixed authors and dates, so their commit IDs are stable. The public replay is rebuilt byte-for-byte from committed inputs. Evidence bundles are checked by recomputing every hash.

Recorded values come from what Tender wrote while a run executed. Derived values are computed from recorded ones. Values a record never captured are shown as unknown, never as zero. See the evaluation errata for defects found in earlier versions and how they affect old records.

05 · Limitations and security boundaries

What a pass does not mean.

  • Checks, not proof. Acceptance means the target and regression checks you configured passed in a clean workspace. A finite test suite cannot show the absence of every regression.
  • Code under test runs with the test runner. Tender resets test files and runner configuration, rejects tool-shadowing modules, and requires named tests in a JUnit report, but a patch built specifically to forge results could still mislead a check.
  • Docker is the boundary. It depends on the host Docker daemon. The local backend runs on your machine and is for patches you wrote or fully trust.
  • Local repositories only. Remote repository sources and pull-request execution are disabled until their isolation is reviewed.
  • Evidence is hashed, not signed. Bundles detect modified, missing, or added files; they do not prove who produced them.
  • Experiments are small. Three synthetic tasks and one quota-limited A/B run. They test the measurement pipeline, not model quality.
