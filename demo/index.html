Verify AI-generated code.

Tender evaluates coding-agent patches against independent tests, records execution evidence, and helps developers understand what actually passed.

Each check runs in a fresh workspace built from a pinned commit. The required tests are fixed by the evaluator, not by the patch. Commands run in a network-disabled container, and the results are sealed with a SHA-256 manifest.

This site is static and read-only: it shows recorded runs and reports, and nothing executes here. A pass means the configured checks passed. It does not prove the code is free of defects.

What Tender does

Verifies a patch

Give it a local repository, a commit, a patch from any agent or person, and acceptance criteria. It returns accepted, rejected, error, or inconclusive, with the reasons.

Evaluates an agent

Runs a bounded agent loop on pinned tasks, with tools authorized at dispatch, and verifies every candidate in a workspace the agent never touched.

Keeps the evidence

Records commands, exit codes, output, test IDs, timings, and digests. Values it never captured are shown as unknown, not as zero.

How independent verification works

Five steps, no hidden ones. The patch and the agent are untrusted, and so is the repository's own Git configuration.

  1. Task or patch. An agent's output, or a .patch file from any tool. The acceptance criteria are written before it runs.
  2. Pinned repository. The commit is resolved from a sanitized copy of .git; repository hooks and helpers never run on your machine. The source is only read.
  3. Isolated execution. The patch is applied to a fresh workspace built from Git objects. Test files and test-runner settings are reset, and hidden tests are added.
  4. Independent checks. A baseline, then target and regression tests, in Docker. Required test IDs come from the base commit, so a patch cannot remove them.
  5. Evidence report. Commands, exit codes, per-test results, coverage provenance, and file hashes, with what remains unknown.

Where things run

Your machine

The Tender process: Git plumbing on sanitized metadata copies, patch validation, report and evidence writing, and a local API and dashboard over SQLite. It never runs repository code.

Docker

Setup, collection, baseline, target, and regression commands. Network disabled, all capabilities dropped, read-only root, non-root user, and CPU, memory, process, and time limits.

This website

Nothing executes. GitHub Pages serves recorded JSON, the dashboard bundle, and a static replay of recorded runs and reports.

Limits of the evidence

  • Checks, not proof. Acceptance means the configured target and regression checks passed. A finite test suite cannot rule out every regression.
  • Same process as the tests. Code under test runs inside pytest. Tender resets evaluator files, fixes required test IDs in advance, and checks report totals. Code built to rewrite the report and force a clean exit could still mislead a check.
  • Docker is the boundary. It relies on the host Docker daemon. The local backend has no isolation and requires an explicit trust flag.
  • Small experiments. One model, three synthetic tasks, and one A/B run dominated by provider quota errors. They exercise the measurement pipeline; they do not rank models.
  • Hashed, not signed. Evidence bundles detect modified or missing files but do not prove who produced them.
  • Local sources only. Remote repositories and pull-request execution are disabled.
